# ADR-087 — `exeris-bot`, the CI publication and capture step (link stub)

**Authoritative copy:** [`exeris-docs/adr/ADR-087-establish-exeris-bot-as-the-ci-publication-and-capture-step.md`](https://github.com/exeris-systems/exeris-docs/blob/main/adr/ADR-087-establish-exeris-bot-as-the-ci-publication-and-capture-step.md)

ADR-087 gives the L2 review one identity to publish under and one contract to publish: two GitHub
Apps (§A.1), a produce step that writes a `verdict` and a publish step that posts, labels and gates it
(§B.5–B.10), and a capture step that emits one ADR-086 run record per L2 run (§C.13–17).

## Why this stub exists

This repository is where the capture step's rows land. §C.15 has the inbox App, `exeris-inbox`,
commit each row — and §C.16 each closed pull request's judgements — directly to `main`; it is the one
bypass actor of this repository's ruleset. **The inbox validator runs twice**, which is what
"reported back to the producer" means operationally: the producer runs `tools/inbox_validate.py`
and the record schema before every write, so a bad row never reaches `main`, and
`.github/workflows/inbox.yml` runs both again on every push to `main`, where a red result files one
issue and reverts nothing. On a pull request to this repository the same two jobs are the required
checks.

A reader who finds a commit by `exeris-inbox` adding files under `inbox/<date>/runs/` or
`inbox/<date>/judgements/`, and asks what decided their shape and why they arrive without a pull
request, is asking about ADR-087 §C.

Engineering Protocol 8 of the ADR owes this stub; it is paid here.
