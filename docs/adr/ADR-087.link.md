# ADR-087 — `exeris-bot`, the CI publication and capture step (link stub)

**Authoritative copy:** [`exeris-docs/adr/ADR-087-establish-exeris-bot-as-the-ci-publication-and-capture-step.md`](https://github.com/exeris-systems/exeris-docs/blob/main/adr/ADR-087-establish-exeris-bot-as-the-ci-publication-and-capture-step.md)

ADR-087 gives the L2 review one identity to publish under and one contract to publish: two GitHub
Apps (§A.1), a produce step that writes a `verdict` and a publish step that posts, labels and gates it
(§B.5–B.10), and a capture step that emits one ADR-086 run record per L2 run (§C.13–17).

## Why this stub exists

This repository is where the capture step's rows land. §C.15 says rows arrive as pull requests rather
than pushes, one per source repository per UTC day, and that **the inbox validator runs on every one
of them** — which is what "reported back to the producer" means operationally. That validator is
`tools/inbox_validate.py` here, run by `.github/workflows/inbox.yml` on every inbox pull request and
by the producer before it opens one, so a bad row never enters the batch; it becomes the required
check once the organisation applies its ruleset to this repository.

A reader who finds a pull request opened by `exeris-inbox` adding files under `inbox/<date>/runs/`,
and asks what decided their shape and why they arrive as a proposal rather than a push, is asking
about ADR-087 §C.

Engineering Protocol 8 of the ADR owes this stub; it is paid here.
